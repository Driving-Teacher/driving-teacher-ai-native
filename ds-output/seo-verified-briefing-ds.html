🧠 먼저 (3분): SEO 신호가 왜 코드 문제인가

검색엔진·AI 봇은 화면을 "사람처럼" 못 읽는다. 그래서 구조화된 신호를 HTML에 박아줘야 한다:

  • JSON-LD = "이 페이지는 기사/강좌/학원, 작성일 X, 가격 Y" 라고 기계가 읽는 라벨. <head>에 <script type="application/ld+json">로 주입.
  • canonical = "같은 내용이 여러 URL일 때 진짜 대표 URL은 이거" 선언. (✅ 이미 전 페이지 적용 — 손댈 것 없음)
  • 301 redirect = "이 URL은 영구히 저 URL로 이사" → 흩어진 링크 권위를 한 페이지로 합침.

핵심: 페이지 유형마다 템플릿 1개가 수천 페이지를 찍어낸다 → 템플릿 1곳만 고치면 수천 페이지가 동시에 고쳐진다.

자기잠식 정리 — canonical/301

🥇 1순위개발 2~4일 + 마케팅 편집결정 · 가치 매우높음

문제 — 같은 키워드를 자사 페이지 여러 개가 경쟁

Google이 "어느 게 대표인지" 못 정해 순위가 나뉜다. 예: 운전면허 필기시험 온라인 접수를 6페이지가 경쟁 → 각자 pos 6~9에서 맴돈다. 총 30개 쿼리에서 발생.

승자/패자 데이터는 이미 산출됨(GSC). 30개 쿼리 각각 winner 1개 + losers N개. 마케팅이 "어느 페이지를 살릴지"만 확정하면 됨. 단, 자동 winner를 맹신 금지 — 아래 케이스 참고.

실측 BEFORE → AFTER (상위 5개 쿼리)

실제 GSC 데이터. 한 검색어에 자사 페이지가 여러 개(빨강) 흩어져 경쟁 → 의도별로 대표를 정리하면 대표 페이지(녹색)가 상위로. AFTER는 보수적 예상치. (시험 도구는 별도 유지, 공부법 블로그끼리 통합 — 아래 케이스 참고)

// pages/academy/[id].tsx  — explore의 Course 생성 코드를 복사 후 단일 학원으로 축소
import Head from 'next/head'
export default function AcademyPage({ academy }) {
  const jsonLd = {
    "@context": "https://schema.org",
    "@type": "DrivingSchool",                 // LocalBusiness 하위 → 지역검색 최적
    "name": academy.name,
    "url": `https://drivingteacher.co.kr/academy/${academy.id}`,
    "image": academy.imageUrl,
    "address": { "@type": "PostalAddress",
      "addressLocality": academy.region, "streetAddress": academy.address }, // explore의 location 재사용
    "aggregateRating": academy.reviewCount
      ? { "@type":"AggregateRating", "ratingValue":academy.rating, "reviewCount":academy.reviewCount }
      : undefined,
    "makesOffer": academy.courses.map(c => ({
      "@type":"Offer", "priceCurrency":"KRW", "price":c.price,
      "itemOffered": { "@type":"Course", "name":c.name }
    }))
  }
  return (<>
    <Head>
      {/* ↓ 이 한 블록만 추가 */}
      <script type="application/ld+json"
        dangerouslySetInnerHTML={{ __html: JSON.stringify(jsonLd) }} />
    </Head>
    {/* 기존 화면 그대로 */}
  </>)
}

H1은 페이지 주제 신호라 페이지마다 달라야 함. 실측 결과 동적 페이지 H1은 이미 콘텐츠별로 잘 생성되고, 홈 1곳만 문제:

홈 H1
운전면허 필기시험부터 운전연수까지 — 운전선생
Google 해석
"이 페이지 = 운전면허 필기시험·운전연수 종합 서비스"

이미 노출되던 head term과 H1 일치 → 관련성 보강 (예: 운전연수 pos 8→6 점진)

⚠️ 솔직한 한계: H1 단독은 보조 신호라 이거 하나로 순위 급등은 없음. 공수 0.5일·리스크 0의 "값싼 정렬 보정"으로, 1·2순위와 함께 홈의 head term 관련성을 받쳐주는 역할.

추가 발견: /blog/0qNC7…는 <h1>이 3개(다른 글은 1개) → blog 템플릿에서 H1 중복 렌더 점검 필요. blog는 "통일"이 아니라 페이지당 H1 1개(=글 제목) 규칙 준수가 핵심.

📁 신규 파일 components/seo/JsonLd.tsx + 사용처 pages/blog/[id].tsx

// components/seo/JsonLd.tsx — 신규 파일 1개 (전 페이지 재사용)
import Head from 'next/head'
export function JsonLd({ data }: { data: object }) {
  return (
    <Head>
      <script type="application/ld+json"
        dangerouslySetInnerHTML={{ __html: JSON.stringify(data) }} />
    </Head>
  )
}

// pages/blog/[id].tsx — 여기에 사용
<JsonLd data={{
  "@context": "https://schema.org",
  "@type": "Article",
  "headline": post.title,
  "datePublished": post.publishedAt,
  "dateModified": post.modifiedAt ?? post.publishedAt,  // ← 수정일 필드 없으면 데이터 쿼리에 추가 = "stale 2024" 해결
  "image": post.coverImage,
  "author": { "@type":"Organization", "name":"운전선생" },
  "publisher": { "@type":"Organization", "name":"운전선생",
    "logo":{ "@type":"ImageObject", "url":"https://drivingteacher.co.kr/logo.png" } },
  "mainEntityOfPage": `https://drivingteacher.co.kr/blog/${post.id}`
}} />

💡 공용 컴포넌트 채택 시 explore 인라인 JSON-LD도 나중에 <JsonLd>로 리팩터 → 전 페이지 스키마 한 컴포넌트로 통일.
